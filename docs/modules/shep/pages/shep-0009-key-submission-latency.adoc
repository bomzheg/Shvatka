== Summary

Typing a key on the site used to wait for the whole game to be *told about it* —
several telegram messages a second apart, then a web push per device of every
player and org. None of that is part of the answer. So an interactor no longer
*shows* anything: it decides what to show, collects it as data in a plain list,
commits, and hands the list over. The api builds its response by reading that
list; telegram and the browser are caught up by a background task afterwards.

== Context

`POST /games/running/key` (`shvatka/api/games/routes.py`) runs
`CheckKeyInteractor` (`shvatka/core/games/interactors.py`) and answers with
`responses.InsertedKey`.

What the request actually waited for, in order:

* `HintSender.send_hints` sleeps `SLEEP` (one second) after the caption and
  after every hint part (`shvatka/tgbot/views/hint_sender.py`). A puzzle of
  three parts is four seconds of sleeping alone, and a level up sends one.
* `WebPushSender.send_many` looped over subscriptions and awaited one blocking
  `webpush` call at a time (`shvatka/api/app/utils/push.py`). A team of eight
  with two devices each is sixteen https round trips in a row — and the same
  again for the orgs in `WebOrgNotifier`.
* `BotOrgNotifier.notify` sends one message per org, one at a time; on the last
  team's last key `all_teams_finished` messages every team.
* All of it inside the transaction: `CheckKeyInteractor` committed *after* the
  fan-out, so the rows the key locked stayed locked for its whole duration.

The one-second sleep is deliberate — it is what keeps the bot inside telegram's
per-chat limits — so the fix cannot be "sleep less".

== Decision

=== What to show is data, decided before the commit

A `ViewTask` (`shvatka/core/views/game.py`) is one thing the game has to show,
as a frozen dataclass over domain dtos: `SendPuzzle`, `WrongKey`, `EffectsKey`,
`GameFinished`, `GameFinishedByAll`, `SendHint`, `ShowEffects`, `DuplicateKey`.
An interactor appends them to a plain `list` while it still holds the
transaction, and shows nothing:

[source,python]
----
tasks = ShowTasks(view=key_tasks(new_key, input_container))
if level_up is not None:
    tasks.extend(level_up_tasks(level_up, ...))
await self.dao.commit()
await self.show(tasks)
----

Before the commit it is a list and nothing else. If the commit raises, the
`show` line is never reached — *a transaction that does not land shows nothing*,
by construction rather than by convention. That is the property the whole shape
exists for, and it cannot be got by deferring at the edge: a view deferred
inside the transaction is still recorded when the transaction rolls back.

`ShowTasks` holds one list per sender — view, org notifier, game log. Order is
kept inside a list and promised nowhere else, because the three senders are
three different audiences.

=== `GameView` is one method

[source,python]
----
class GameView(Protocol):
    async def show(self, tasks: Sequence[AnyViewTask]) -> None: ...
----

The eight `send_puzzle` / `wrong_key` / … methods are gone from the interface.
Each implementation keeps them privately and routes to them by matching on the
task type; `AnyViewTask` is a union, so a view that forgets a task fails to
type-check rather than silently ignoring it.

Two things fall out of this that the old fat interface made expensive:

* *Adding something to show is one task class and one branch per view*, instead
  of a method on the protocol times four implementations plus a forwarder.
* *A view decides how to render a whole batch.* That is what lets the combined
  view hand the batch to the nursery as one job — which is what keeps the
  messages of one key in order.

=== Showing is one background job, spawned by the view

`ComplexView.show` does one thing: `nursery.spawn(show_game, tasks=...)`.
`shvatka/tasks.py` is where a job that touches both edges lives, since it is the
combined app that knows both. It pushes to the browser first (one https call),
then writes to telegram (a caption and its hints, a second apart), containing
and retrying each task on its own — one chat the bot was thrown out of must not
cost the others their puzzle.

The nursery hop is the *view's* business, not the interactor's: core says "show
these", and whether that happens now or in a background job is a property of
where it is being shown. The bot-only app binds `GameView` straight to `BotView`
and renders inline, unchanged.

=== The api answers from the same list

`insert_key` no longer reads a container the views wrote into — it reads what
the interactor returned:

[source,python]
----
tasks = await interactor(key=key.text, identity=identity, input_container=input_container)
shown_key = next((task for task in tasks if isinstance(task, KeyShown)), None)
----

`WebInput` is deleted. It existed only to smuggle a return value back out of a
view, which is why the route had to `logger.critical` and answer 500 when a view
had not been called. `InputContainer` now means only what its name says: what
the key was typed into, so the bot knows which message to reply to. The api
passes `ApiInput`, which holds nothing.

`WebGameView` is left with only what it was really for — pushes — and is
deferred along with the bot half. The site does not need its own push to know
what happened; it has the response.

=== Failures are alerted, not swallowed

Each task is delivered on its own and a failure goes to `BotAlert`, because by
then there is no request to fail. Retries cover what telegram says is its own
fault: `TelegramRetryAfter` (waiting exactly as long as it asked, up to
`MAX_RETRY_DELAY`), `TelegramNetworkError`, `TelegramServerError` — three
attempts, doubling backoff. Being blocked by a chat or sending something
malformed is not retried; the second attempt would fail identically.

`AsyncioNursery.close` waits `drain_timeout` (15 s) for running jobs before
cancelling them, so an ordinary restart mid-fan-out no longer leaves a team with
half a puzzle. Bounded, because other jobs (publishing a scenario to the forum)
are minutes long and a restart cannot wait them out.

*Accepted cost:* a retry restarts the whole task, and rendering one task can be
several messages, so a failure halfway through a puzzle resends the parts that
arrived. Deliberate — a duplicated puzzle is confusing, a half-sent one leaves
the team with nothing to solve.

*Still lost:* a hard kill (SIGKILL, OOM) during a delivery, and anything the
drain gives up on. Durable delivery is xref:shep-0010-message-outbox.adoc[SHEP-0010].

=== Decide, commit, then show

`GamePlayBaseInteractor.process_level_up` used to interleave the two — read
whether the team finished, show it, read whether everyone finished, write
`dao.finish`, show that — so a view always ran inside the transaction and a
finished game needed a second commit to land. It is now two halves:

* `resolve_level_up` does the locking, the reads and the one write
  (`dao.finish`), and returns a `LevelUpOutcome` carrying everything a view
  will need;
* `level_up_tasks` turns that outcome into tasks — a pure function, no `self`,
  no io, so what a level up shows is unit-testable on its own.

`CheckKeyInteractor` resolves, commits once, then shows. `GamePlayTimerInteractor`
follows the same order, so "no view inside a transaction" holds on both paths
into a level up.

The key is a fact of the game the moment it is typed; holding its rows for the
length of a chat conversation was never intentional.

=== Pushes go together

`WebPushSender` sends up to `PARALLEL` pushes at once and disables the
subscriptions the provider reported gone *after* the gather, on the request's
session — a session only one coroutine at a time may touch. The orm objects
stay on the event loop: only plain values (`_Recipient`) are handed to the
sending thread.

== Consequences

* The endpoint answers in about a database round trip; the response payload is
  unchanged, so the front-end needs no change.
* The site shows a level up before the team's chat does. Harmless — a player
  typing the next key early is a wrong key at worst — but it is a real ordering
  change between the two edges.
* An interactor that shows something must remember to call `show` after its
  commit. There is no finalizer catching what it forgot, and that is on purpose:
  a flush that runs whatever happened would also run after a rollback.
* Scheduled hints go out the same way: `send_hint` collects one `SendHint` and
  shows it, so the job finishes as soon as the task is handed over.
* A view task must be self-contained — it is rendered later, in another scope.
  `AGENTS.md` carries the rule.
* `ComplexGameViewPreparer` and `ComplexTeamNotifier` still send inline. They
  are not on the key path (game start, team membership) and can move later.
* `OrgNotifier.notify` and `GameLogWriter.log` take a sequence now, so every
  caller wraps its event in a list. Mechanical, and it is what lets one request
  be one job per sender.

== Deviations from the plan

Twice, both times because review found a weaker version of the same rule.

The first cut committed twice — once for the key, once at the end for the
`dao.finish` a level up may have written — because the level up mixed writes and
views. That became `resolve_level_up` / `show_level_up`, one commit with the
views after it.

The second cut deferred at the *edge*: the bot half of each view call was
recorded as a closure into a request-scoped `BotOutbox` and flushed by its
dishka finalizer. It answered fast, but it kept two weaknesses this document
originally accepted: dishka finalizes generator providers with
`asend(exception)`, so the flush ran *even when the request raised* — a view
recorded before a failed commit would have been shown anyway; and a closure
cannot be anything but run, which put the whole of
xref:shep-0010-message-outbox.adoc[SHEP-0010] behind a rewrite. Moving the
decision into the interactor as data fixed both and deleted more code than it
added.

== Open questions

* How long does the endpoint actually take now? There is no measurement of the
  fan-out — `asgi_monitor` exposes the route's histogram, but the split between
  database, push and telegram is guesswork.
* `ComplexTeamNotifier` and `ComplexGameViewPreparer` are the last inline
  senders. Are they worth converting to tasks for uniformity, or is "not on a
  hot path" a good enough reason to leave them?
